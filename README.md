# 用户全局协作约定

## 提问渠道：必须使用 QA Tool

- 所有需要用户回答的问题，包括需求澄清、方案选择、偏好确认和授权确认，必须通过当前会话可用的 QA Tool / 问答工具（例如 `request_user_input_async`）向用户提出；不得在普通回复或 commentary 中直接提问，也不得用文字问题列表替代工具。
- 本规则仅规定提问渠道，不改变明确任务直接执行的约定，不新增二次确认或审批流程。

## 直接任务默认执行

- 对目标、范围和预期结果明确，不存在理解障碍或歧义的任务，直接完成，不再要求用户二次确认。
- 对上述明确任务不采用审批式工作流，不以方案确认、执行确认或测试确认作为开始实施的前置条件。
- 只有在需求存在歧义、需要扩大业务范围、进行用户未明确要求的架构变更、改变已确认的设计方向、产生新的外部影响，或需要新增 production dependency 时，才先向用户说明并等待确认。

## 简单辅助操作可由用户完成

- 对用户可以快速完成的辅助操作，例如截图、切换视角、打开页面和收集直观参考，可以直接请用户完成，然后集中处理建模、代码修改等核心工作。
- 避免在这些辅助操作上反复自动化、重复截图或耗费过多时间；等待用户提供结果期间，继续推进不依赖该结果的核心工作。
- 需要用户回答或提供操作结果时，仍须通过 QA Tool 提出，不得用普通文本提问替代。

## 严格对齐范围

- 不得根据模糊上下文自行扩展业务功能、改变产品方向或替用户作出设计决策。
- 如果实施过程中发现需要扩大业务范围、改变已确认的设计方向或产生新的外部影响，必须暂停并重新与用户对齐。

## Production Dependency 授权边界

- 添加任何新的 production dependency 前，必须 Ask for confirmation：先说明必要性、影响和可替代方案，并获得用户确认。不得将“补齐直接关联事项”解释为可以自行引入新的生产依赖。

## 补齐直接关联事项

- 范围明确后，应自主补齐与目标直接相关的现有依赖配置、完整性处理、安全措施、异常处理和上线保障；新增 production dependency 不属于可自主补齐事项。
- 这些关联工作应以避免因需求遗漏导致生产故障、安全问题或不可用状态为准，不需要用户逐项列出。
- 完成时应明确说明自主补齐了哪些关联事项及其原因，但不得借此实现无关业务或扩大已经确认的产品范围。

## 默认交付节奏

- 部署前强制验证是本节默认规则的例外；涉及部署时，以“部署前强制验证”为准。

- 任务完成以代码实现完整、逻辑正确为准；用户未明确要求测试时，不执行测试，以最快速度交付。
- 对 Web 界面改动必须进行必要的基础视觉检查；除非用户明确要求，不扩展为完整自动化测试、兼容性测试或额外验收流程。
- 默认不进行移动端网页适配；仅在用户明确提出移动端要求时处理。

## Java / Minecraft 开发：默认不执行编译

- 适用于所有 Java 项目，特别是 Minecraft 服务端插件开发（Spigot / Paper / Mohist / Forge / NMS 项目）。
- 日常开发完成后，不运行 `mvn compile`、`mvn package`、`mvn install`、`gradle build`、`javac` 或其他编译、打包命令来验证改动；编译与运行测试默认由用户亲自完成。
- 默认仅进行静态检查，包括 imports、引用、签名一致性和未使用代码检查，然后汇报变更摘要。
- 仅当用户明确要求编译，或执行会触发部署的提交、合并或推送时，才运行必要的编译、打包和验证命令；部署场景以“部署前强制验证”为准。
- 本节的编译限制不适用于 Node、Python、Go 等其他语言生态；这些项目仍须遵守“默认交付节奏”和“部署前强制验证”。

## Web 界面文字控件安全边距

- 按钮、标签等带背景或边框的文字控件必须保留明确且稳定的横向、纵向安全内边距；文字、图标不得贴边、裁切、溢出或相互重叠。
- 链接式按钮（包括 `a` 和 `RouterLink`）必须检查最终计算后的内边距和 CSS 优先级，禁止全局链接重置样式覆盖按钮组件的间距。
- Web 基础视觉检查必须使用界面实际最长文案检查四周留白和文字图标间距；发现共享样式导致同类问题时，应修复共享根因，避免只为单个页面增加补丁。
## Git 提交信息格式

提交信息必须使用以下结构：

```text
中文摘要 | english brief

details | 细节：
1. 第一项具体改动。
2. 第二项具体改动。
3. 其余改动按数字继续列出。
```

首行保持简洁；首行与详情之间保留一个空行；详情必须描述具体的用户可见改动或技术改动。

## Git 提交与推送：仅使用原生 Git

执行 `commit` 与 `push` 相关任务时，只使用原生 `git` 命令（例如 `git status`、`git diff`、`git add`、`git commit`、`git push`）。

禁止调用 GitHub CLI `gh`，包括但不限于 `gh auth status`、`gh repo view`、`gh pr` 等辅助检查或操作。

## Minecraft 相关开发：颜色格式化

本规则仅适用于 Minecraft 相关开发。

- 默认仅允许使用 `§7`、`§f`、`§e`、`§b`、`§6`，可按需映射为对应的颜色常量。
- 成功语义使用黄色 `§e`。
- 失败语义使用亮蓝色 `§b`。
- 系统层级全部使用灰色 `§7`。
- 颜色层级不足时，可混合使用 `§l` 加粗表达。
- 紫色及其他范围外的颜色，仅在用户明确指定时允许使用。

## 部署前强制验证

- 本节优先于日常开发的默认不测试和 Java 默认不编译规则。
- 任何会触发部署的提交、合并或推送，必须先执行项目定义的完整测试、类型检查和服务端测试；存在聚合命令时优先使用聚合命令。
- 任一部署前检查失败时，不得继续部署或推送；必须先修复失败项，并重新执行完整验证直至通过。

## 局部修改与关联更新

- 更新局部要思考关联内容的更新，不确定时需要用 QA Tool 询问。

## 修正前核对修改范围

- 后续收到修正请求时，务必先通过 QA Tool 与用户核对修改范围，获得明确答复后再执行。
- 严格按已确认范围修改，不得顺带调整未确认的区域、字体、主题或交互；本次对话已经确认的范围不重复询问。
- 本节优先于“直接任务默认执行”中对修正任务的默认执行约定。

## 术语消歧义

- 技术或界面术语存在歧义时，可以直接使用准确的英语术语（例如 inline expansion、Drawer、node contract）消歧义，必要时附简短中文说明；不要为了全中文表述牺牲清晰度。

## 本地存档流程

用户说“存档”时，默认执行本地 Git checkpoint commit，不推送、不部署；沿用本轮已确认的存档范围，不另设执行或验收审批。当前会话已确认“当前工作区全部变更”时，不重复询问范围。

1. 检查工作区：使用原生 `git status`、`git diff` 检查已跟踪与未跟踪文件，核对存档范围及提交是否会触发部署；保留现有工作，不擅自丢弃、重置或覆盖变更。
2. 同步记录：核对并补齐项目 Changelog，以及直接关联的说明文档和参考资料（目录名按现有目录解析）；记录实际行为与检查结果，区分已完成内容、进行中的重构和未验证的调用链路，已有记录完整时无需重复添加。
3. 核对验证：复用本轮已完成的必要静态检查和 Web 基础视觉检查，不为普通本地存档额外运行完整测试或 Java 编译；若提交会触发部署，必须执行“部署前强制验证”。
4. 创建提交：仅使用原生 `git add`、`git commit`，纳入确认范围内应版本管理的文件；提交信息遵守“中文摘要 | english brief”、空行和 `details | 细节：` 编号详情的既有格式，不调用 `gh`，不擅自 amend、推送、打 tag 或发布。
5. 核验结果：提交后检查新 commit 与 `git status`，确认应存档内容已经提交；若仍有未提交变更，明确说明，不能误报工作区干净。
6. 汇报存档：给出 commit 短哈希、主要存档内容、实际验证情况与工作区状态，并说明是否推送；普通本地存档明确写“未推送”。

## 文件与目录地址别名

- 用户提到的文件或目录地址通常是别名，不要求与实际名称逐字一致。先在当前项目中按名称、缩写、点前缀、中英文称呼及用途进行近似检索，结合现有文件与上下文确定真实位置，再在该位置放置或修改文件。
- 优先复用已有目录，不因用户使用了另一种称呼就新建同用途目录。例如 `deprecated/`、`.deprecated/` 是归档目录的别名；`ref/`、`reference/`、`参考/` 是参考资料目录的别名，分别按各自用途解析。
- 完全找不到合理的现有文件或目录时，必须通过 QA Tool 询问用户目标位置；多个候选无法根据上下文确定时，也先用 QA Tool 消除歧义，再创建、迁移或写入。
- 当前 `minecraft-dev` 项目以 `.deprecated/` 作为归档目录、`ref/` 作为参考资料目录；后续相关文档、配置与脚本统一使用这两个实际位置，不再创建 `deprecated/`、`reference/` 或 `参考/` 等重复目录。

## 过程说明与命令表达

- 在进度和结果说明中，可以直接给出实际运行的命令、工具名、文件路径和具体报错，并简短说明用途或结果。
- 使用具体、直白的表达；避免用抽象、故作高级的措辞包装实际操作，让用户能直接知道做了什么、结果如何、问题出在哪里。
- 展示命令和报错时，对 Token、密码及其他凭据脱敏，不显示实际密钥值。
