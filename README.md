## 为什么需要这些规则

Codex 的 capability security 已经比较完整，但 authority / intent security 还明显不成熟。

Capability security 解决的是“Agent 能不能执行某项操作”；authority / intent security 解决的是“这项操作是否得到用户授权，以及是否仍然符合用户的真实意图”。沙箱和命令审批可以限制能力，却不能替用户作出产品、范围或架构决策。

Codex 存在明显的 agentic overreach / scope-expansion bias，容易出现下面的路径：

```text
发现潜在问题
    ↓
自行决定解决方案
    ↓
修改架构
```

“发现问题”并不等于“获得了解决该问题的授权”。因此，这套规则允许 Codex 在明确范围内自主完成工作，但在扩大业务范围、进行用户未要求的架构变更、改变设计方向、产生新的外部影响或新增 production dependency 前，必须先获得确认。

## 验证强度

规则按风险分为三个层级：

1. 普通实现：速度优先，不默认扩展测试、review 或额外验收流程。
2. Web UI：必须进行基础视觉检查，因为成本低、发现布局与样式问题的收益高。
3. 部署操作：必须执行完整验证，因为这时已经会产生真实的外部影响。

默认追求快速实现和人工检查，并不意味着部署时可以跳过验证。Web 视觉检查与部署前完整验证是两个明确例外。

## 规则及其原因

### 直接任务默认执行

| # | 规则 | 原因 |
| --- | --- | --- |
| 1 | 明确任务直接完成，不重复确认 | 已经清楚的目标不需要再次走确认流程。这样可以减少无效往返、等待时间和 token 消耗。 |
| 2 | 不把方案确认、执行确认或测试确认作为开工前提 | 对明确任务使用 approval-style workflow 通常不会增加新的有效信息，只会降低交付速度。 |
| 3 | 只在歧义、范围扩大、未授权架构变更、设计变更、新外部影响或新增 production dependency 时确认 | 这些情况需要新的 authority，不能由 Agent 根据上下文自行推断。把例外写清楚，也能防止“直接执行”被误解为无限授权。 |

### 严格对齐范围

| # | 规则 | 原因 |
| --- | --- | --- |
| 4 | 不自行扩展功能、改变产品方向或替用户作设计决策 | 潜在问题不是修改产品或架构的授权。这条规则用于抑制 agentic overreach 和 scope-expansion bias。 |
| 5 | 实施中发现必须扩大范围时，暂停并重新对齐 | 如果等到 Agent 已经修改架构后才告知用户，确认就失去了意义，所以对齐必须发生在变更之前。 |

### Production Dependency 授权边界

| # | 规则 | 原因 |
| --- | --- | --- |
| 6 | 新增任何 production dependency 前，先说明必要性、影响和替代方案，并获得确认 | 新依赖会长期影响 supply-chain security、许可证、构建、部署、包体积和维护成本。这是用户应当决定的产品与工程取舍，不能因为 Agent 有能力安装就视为已经获得授权。 |

### 补齐直接关联事项

| # | 规则 | 原因 |
| --- | --- | --- |
| 7 | 自主补齐现有依赖配置、完整性、安全、异常处理和上线保障 | 只机械实现显式文字，可能交付一个无法使用或容易产生生产故障的结果。明确范围内的必要完整性处理不应反复询问，但这不包括引入新的 production dependency。 |
| 8 | 补齐工作仅限于避免故障、安全问题或不可用状态 | 这给“必要补齐”设置了可以判断的边界，防止它再次成为 scope expansion 的理由。 |
| 9 | 完成时说明补齐了什么以及为什么 | 保留可审计性，让用户能够快速判断 Agent 是否越界，以及额外处理是否真的与目标直接相关。 |

### 默认交付节奏

| # | 规则 | 原因 |
| --- | --- | --- |
| 10 | 用户未要求时不扩展测试，以最快速度交付 | 实际使用中，长时间 review、自动检查和反复修正命令会消耗大量时间与 token，但最后仍可能遗留不少问题。对非部署任务，人工检查通常具有更高的投入产出比。Codex 的 command spelling 可靠性也仍有提升空间，错误命令及其修正循环经常额外消耗时间。 |
| 11 | Web 界面改动必须进行基础视觉检查 | Codex 的内置浏览器是相比没有内置浏览器的 Claude Code 的重要优势。很多 UI 问题只能通过实际渲染快速发现，例如按钮排列不合理、按钮大小不一致、文字紧贴边缘、padding 不足或内容溢出。 |
| 12 | 默认不做移动端适配 | 移动端会引入额外 breakpoint、布局与兼容性工作，显著增加时间和 token 成本。未明确要求时，它应被视为独立范围，而不是桌面端页面的默认附加项。 |

### 部署前强制验证

| # | 规则 | 原因 |
| --- | --- | --- |
| 13 | 会触发部署的提交、合并或推送前，运行完整测试、类型检查和服务端测试 | 部署会产生真实的外部影响，此时生产回归的成本高于节省的检查时间，因此必须提高验证等级。 |
| 14 | `lingkun-web` 固定使用 `npm run test:all` | 聚合命令能提供一致、可复现的验证范围，并减少漏掉检查步骤的风险。Codex 经常在临时拼接 command 时出现拼写错误，因此优先复用项目定义的准确命令，也能避免在错误命令上浪费时间与 token。 |
| 15 | 任一检查失败时禁止继续部署，修复后重新执行完整验证 | 已知失败不能被带入生产；重新运行完整验证可以避免修复一个问题时引入新的回归。 |
